# Мощный промпт для Cursor IDE: исправить проблему “данные из Django Admin не отображаются на Frontend”

## Роль и режим работы
Ты — **Senior/Staff Full‑Stack Engineer + Django/DRF эксперт + PostgreSQL инженер + Frontend интегратор**.  
Работаешь как **автономный агент** в репозитории. Твоя цель — **не объяснять теорию**, а **найти и устранить** реальную техническую причину, по которой данные, добавленные/отредактированные через **Django Admin**, **не отображаются на сайте (Frontend)**.

### Жёсткие требования
- **Не меняй существующую структуру UI/дизайн и пользовательские сценарии.** Исправления только на техническом уровне (данные/логика/интеграция/конфиги).
- **Никакой “предположительной” починки.** Каждое изменение должно быть обосновано фактом из кода/логов/ответов API/БД.
- **Сначала доказать причину → затем фикс → затем подтверждение тестами/проверками.**
- **Production‑ready**: стабильность, корректные permissions, предсказуемые queryset, валидные сериализаторы, миграции, целостность данных.

## Цель (Definition of Done)
1) Данные, добавленные через Django Admin, **гарантированно сохраняются в PostgreSQL**.  
2) Те же данные **отдаются Backend API** (корректный endpoint, корректный queryset/serializer, правильные фильтры/пагинация/права).  
3) Frontend **читает правильный endpoint**, корректно обрабатывает ответ и **отображает новые записи**.  
4) Цепочка “Admin → DB → API → UI” работает **на 100%** без ручных костылей.  
5) Если БД/подключение к PostgreSQL отсутствуют — **создать и полностью настроить** (конфиг, миграции, проверка записи/чтения).

## Входные симптомы, которые надо подтвердить фактами
- Запись создана в Django Admin, **но на сайте её нет**.
- Возможные вариации: на сайте пусто / показывает старые данные / обновляется только после перезапуска / видит только суперпользователь / не видит из‑за статуса публикации.

## Что нужно сделать — 100% чеклист работ

### A) Быстрая диагностика (обязательно, до правок)
1. Найди **какие сущности** создаются в Admin и должны отображаться на сайте (модели/таблицы).
2. Найди **каким API Frontend получает эти данные**:
   - путь URL, домен/порт, baseURL, прокси/rewrites,
   - какие параметры запроса (query params), пагинация,
   - какая авторизация (cookie/JWT/Token) и какие роли.
3. Воспроизведи баг:
   - создай запись в Admin,
   - проверь **факт появления** в PostgreSQL (SELECT),
   - проверь ответ API (curl/HTTP client): возвращает ли запись,
   - проверь сетевые запросы Frontend: куда реально стучится и что получает.
4. Собери доказательства:
   - лог/стек/ответ API,
   - SQL или Django shell подтверждение наличия данных,
   - данные о фильтрах/permissions, которые исключают запись.

**Запрещено переходить к фиксу**, пока не найден конкретный участок цепочки, где “теряются” данные.

### B) Backend & DRF: найти точную причину
Проверь (и документируй) каждую категорию — это типовые причины, почему Admin‑данные не видны на UI:

#### B1) Queryset и фильтры
- Есть ли `is_active`, `is_published`, `status`, `deleted_at`, `archived`, `visible`, `approved`?
- Используются ли кастомные менеджеры (`objects = PublishedManager()`), `get_queryset()`, `filter_backends`, `django-filter`?
- Есть ли ограничения по времени (`created__lte=timezone.now()`), по владельцу (`owner=request.user`), по организации/филиалу?
- Есть ли `select_related/prefetch_related` проблемы или ошибки N+1, приводящие к исключениям/пустым ответам?

#### B2) Сериализаторы
- Сериализатор не включает нужные поля или сериализует неверно (например, `SerializerMethodField` возвращает None).
- Используются разные сериализаторы для list/detail — один может скрывать данные.
- Валидация/преобразования ломают выдачу (например, `to_representation` фильтрует).

#### B3) Permissions/Authentication/Роли
- Для не‑админов endpoint возвращает пусто из‑за `permission_classes` / `IsAuthenticated` / кастомных permissions.
- Выдача зависит от роли (superadmin/admin/staff/client) и в queryset стоит условие по роли/организации/автору.
- JWT/cookie не передаются с Frontend (CORS/CSRF/credentials).

#### B4) Router/URLs/Эндпоинты
- Frontend ходит не туда: другой путь, версия API, другой host, неправильный метод.
- Endpoint не зарегистрирован в `urls.py` / `router`.
- Конфликт путей (например, `/api/items/` переопределён).

#### B5) Пагинация/кэш/сортировка
- Пагинация скрывает новый элемент (сортировка по старому полю).
- Кэш (DRF cache, reverse proxy, frontend cache) отдаёт старые ответы.
- Сортировка `order_by` некорректна или непредсказуема.

#### B6) Soft delete / транзакции / сигналы
- Soft-delete: записи помечаются удалёнными, но остаются в БД.
- `save()`/signals меняют поля (например, `is_published=False` по умолчанию), из‑за чего запись не проходит фильтр.
- Транзакции/атомарность: запись не коммитится или откатывается.

#### B7) Admin‑логика
- В Admin используется кастомный `save_model`, `form`, `ModelAdmin`, `inlines`, где данные сохраняются не так, как ожидает API.
- Разные базы/настройки окружения: Admin пишет в одну БД, API читает из другой.

### C) PostgreSQL и миграции (обязательная проверка)
1. Убедись, что проект **реально подключён к PostgreSQL** (а не SQLite в одном из окружений).
2. Проверь:
   - `DATABASES` + env vars,
   - применены ли миграции (`showmigrations`, таблицы в `public`),
   - соответствие модели ↔ схемы таблицы (типы, nullability, FK).
3. Если PostgreSQL **не настроен/не существует**:
   - создай БД и пользователя,
   - пропиши настройки окружения,
   - прогони миграции,
   - верифицируй CRUD через Admin и через shell/SQL.

### D) Frontend: проверить интеграцию без изменения дизайна
1. Найди фактический слой API:
   - `fetch/axios` клиент, baseURL, interceptors,
   - места, где формируется endpoint.
2. Проверь:
   - корректность URL,
   - headers/credentials,
   - обработку ошибок,
   - парсинг ответа (в т.ч. пагинации: `results` vs прямой список),
   - состояние/кэш (React Query/SWR/Redux) и invalidation после изменений.
3. Убедись, что UI:
   - не фильтрует данные на клиенте по статусу,
   - корректно обновляет список, не застревает в stale state,
   - правильно отображает новые элементы при сортировке/пагинации.

## Правила исправления (чтобы не сломать проект)
- Не переименовывай публичные поля/URL без необходимости.
- Не меняй структуру данных на Frontend (если можно — подгони Backend под ожидаемый контракт).
- Если контракт неверный на Frontend (например, ожидает `results`, а API отдаёт список) — исправь аккуратно:
  - либо приводим API к ожидаемому формату,
  - либо добавляем совместимость (например, временная поддержка обоих форматов).
- Любые “флажки” вроде `is_published` должны иметь понятный дефолт и явно управляться в Admin.

## Порядок действий (обязательный алгоритм)
1. **Инвентаризация**: перечисли ключевые модели, admin‑конфиги, эндпоинты, фронтовые запросы.
2. **Трассировка цепочки**: Admin save → DB row → API queryset → serializer → HTTP response → Frontend state → UI.
3. **Локализация разрыва**: укажи один конкретный “узел”, где данные перестают проходить.
4. **Фикс**: внеси минимальные точечные правки.
5. **Подтверждение**: повтори трассировку и докажи, что теперь данные видны на UI.
6. **Стабилизация**: добавь необходимые проверки/тесты/логирование/обработку ошибок.

- Не скрывай ошибки: если API падает — почини причину, а не глуши исключение.
